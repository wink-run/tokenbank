# 设备网络 · 测试手册

分支：`claude/personal-device-mesh-prototype`。先跑「一、自动回归」确认环境没问题，再按「二」到「九」用两台真机逐项测。每项写了**怎么做**和**应该看到什么**，对不上的记下编号、截图和两台设备的日志（命令行版在终端输出里，带 `[mesh]` 前缀）。

## 二、准备两台真机

**服务端**（测试环境，`.env` 加上）：

| 变量 | 值 |
|---|---|
| `MESH_ISSUER_KEY` | `python3 -c "import os;print(os.urandom(32).hex())"` 生成，多实例用同一个 |
| `MESH_RELAY_URLS` | 先不填（只测直连）；测中继时再填，见第九节 |
| `MESH_RELAY_ACCESS_TOKEN` | 随便一串，测中继时用 |

重新部署后，`pip install -r requirements.txt` 会装上新依赖 `cryptography`。

**两台电脑**：A（比如笔记本）、B（比如台式机 / Mac mini），同一个 TokenBank 账号登录，客户端都指向上面的测试服务端。B 上装好至少一个命令行智能体（Claude Code 或 Codex），最好也配一个本地模型（Ollama）。B 上准备一个 git 仓库（有至少一个提交），A 上也克隆一份同一个仓库（测取回改动用）。

每台的智能体 Key 在 `~/.llm-agent/local-config.json` 的 `agent_api_key`，下面的 `curl` 里写成 `$KEY`，网关默认 `http://127.0.0.1:11430`。

## 三、入网（E1）

| # | 怎么做 | 应该看到 |
|---|---|---|
| 3.1 | 两台都登录。打开「盘点」，选中「这台电脑」 | 「改名」下面一行有「设备网络」开关，旁边写「打开后自动领设备证书…」 |
| 3.2 | 两台都打开「设备网络」 | 几秒后出现「已和云端同步 · 地址簿里 1 台」；接活、同时接、开放本机模型、工作区几个开关出现 |
| 3.3 | 网关页、模型页、游乐场 | 多出「所在设备」列 / 设备标签，能看到对方设备的名字（见第五节） |
| 3.4 | `curl -H "Authorization: Bearer $KEY" localhost:11430/v1/devices` | 两台都在，对方 `online: true`，`connection` 是 `direct`（同一局域网）|
| 3.5 | 一台退出登录 | 那台的设备网络停止，另一台看到它离线 |
| 3.6 | 重新登录 | 自动重新入网，不用再点开关 |
| 3.7 | 在「个人页」的设备列表里删除 B | 1 分钟内 A 断开 B（A 日志 `已被吊销，断开`），B 再也连不上 A |
| 3.8 | 删除后 B 重新登录、重新打开设备网络 | B 重新注册、领到新证书，恢复正常 |
| 3.9 | 用**另一个账号**登录第三台设备并打开设备网络（同一局域网） | 它看不到前两台，前两台日志里有 `other_user` |

## 四、统一入口（E2）

**模型**

| # | 怎么做 | 应该看到 |
|---|---|---|
| 4.1 | B：盘点 → 本机 → 打开「开放本机模型」 | A 的「模型 · 账户」里出现一行「B 的模型源 · 其他设备开放的」，所在设备标 B |
| 4.2 | A 上没有、B 上有的模型（比如 Ollama 的 `qwen3:8b`），在 A 的游乐场「模型对话」里用 | 由 B 回答；A 网关页「路由」明细里这条标着 B |
| 4.3 | A 和 B 都有同一个模型 | 先用 A 本机的；把 A 那个源停掉后自动换到 B |
| 4.4 | 指定设备：模型名写 `mine:<B 的名字>/<模型>` | 一定在 B 上做 |
| 4.5 | B 关掉「开放本机模型」 | A 的账户表里那行消失，4.2 改为报找不到模型 |
| 4.6 | B 的路由明细 | 从 A 来的请求，详情里「发起设备」是 A |

**智能体**

| # | 怎么做 | 应该看到 |
|---|---|---|
| 4.7 | `curl -H "Authorization: Bearer $KEY" -H 'content-type: application/json' localhost:11430/v1/agent/responses -d '{"input":"看看仓库里有什么","metadata":{"harness_id":"mine:claude-code@<B 的名字>","workspace":"<B 的工作区名>"}}'` | 在 B 的那个仓库里执行，结果回到 A，任务号是 `mesh:<B>:…` |
| 4.8 | A 的游乐场「智能体路由」输入 `/claude-code@<B 的名字> 看看仓库` | 跳过主智能体，直接在 B 上做；路由明细显示「指定」和 B |
| 4.9 | 盘点里给 B 改名（比如 `studio`） | 交易页「设备名称」同步变成 studio；之后 `@studio` 能派活，原来的电脑名也还能用 |
| 4.10 | B 关掉「接我其他设备派来的活」 | A 上 B 的应用、智能体消失；派给 B 的活报「没有…」 |
| 4.11 | B 的「同时接」设成 1，A 同时派两个慢任务给 B | 第二个立刻返回「这台设备正在跑 1 个任务，满了」（429） |

## 六、协作完成大任务（E4）

前提：A 上游乐场「智能体路由」能用（主智能体是 Claude Code 或 Codex）。

| # | 怎么做 | 应该看到 |
|---|---|---|
| 6.1 | 智能体路由里给一个能拆开的任务，比如「给登录页加记住我，同时写接口文档、补单测」 | 主智能体先用 `tb_ask` 列出拆分计划等你确认（检查点）；游乐场显示它在等回答 |
| 6.2 | 回答「可以」 | 主智能体把互不依赖的子任务用 `background` 并行派出（可以派到 B） |
| 6.3 | 输入框上方的任务板 | 「子任务 · N」：每个子任务的智能体、所在设备、状态；做完的显示改了几个文件、几个产出文件 |
| 6.4 | 子任务在 B 上改代码 | B 上**你自己的工作区没被动**（`git status` 不变）；B 的 `~/.tokenbank/mesh/worktrees/` 下多了工作树，分支 `tb/collab/<父任务>/…` |
| 6.5 | 两个子任务同时改同一个仓库 | 各在各的工作树，互不覆盖 |
| 6.6 | 任务板上点某个子任务的「取回改动」 | A 本机仓库多一个分支 `tb/mesh/<任务号>`，当前分支不变；`git diff HEAD...tb/mesh/<任务号>` 能看到改动 |
| 6.7 | 子任务遇到问题提问 | 任务板那张卡变黄「在等回答」，显示问题；在卡片里回答 → 它接着原来的会话做完 |
| 6.8 | 任务板「叫停」一个在跑的子任务 | 状态变「已叫停」，B 上那个进程停掉 |
| 6.9 | 任务板「改派」一个失败的子任务给另一个智能体 / 设备 | 多出一张新卡，同样的任务在新目标上跑 |
| 6.10 | 主智能体合并前 | 再停一次（检查点），说明要合哪些、测试结果，等你确认 |
| 6.11 | 请求里带 `"metadata":{"checkpoints":"none"}` | 不再停下来问 |
| 6.12 | 同时续同一个子任务两次（`previous_response_id` 相同） | 第二个返回 409「已经有一轮在接着它做」 |
| 6.13 | `GET /v1/agent/responses/<主任务号>?tree=1` | 整棵任务树，B 上的子任务标着 `mesh_device` |
| 6.14 | 网关 · 路由明细里点一条子任务 | 详情里有「父任务」 |

MCP 工具（主智能体自己会用，也可以在 Claude Code 里手动调）：`tb_list_agents`（列出 `mine:…@设备`）、`tb_dispatch_agent`（`background`、`previous_task_id`）、`tb_task_status`（`wait: any/all`，默认只给摘要，`detail: true` 给全文）、`tb_ask`、`tb_collect`。

## 七、产出和远程查看（E5）

把 `<id>` 换成一个在 B 上改过代码、出了报告的任务号（`mesh:…`）。

| # | 命令 | 应该看到 |
|---|---|---|
| 7.1 | `curl -H "Authorization: Bearer $KEY" "localhost:11430/v1/agent/responses/<id>"` | 有 `git`（改动统计、`refs/tokenbank/mesh/…`）和 `artifacts`（产出文件清单，含 sha256） |
| 7.2 | `curl -H "Authorization: Bearer $KEY" "localhost:11430/v1/agent/responses/<id>/artifacts/file?path=<清单里的 path>&sha256=<清单里的>" -o out.bin` | 拉回原文件 |
| 7.3 | 在 B 上把那个报告改掉，再拉一次 7.2 | 还是原样（从快照 `~/.tokenbank/mesh/outbox/` 拿）；sha256 写错时回 409 |
| 7.4 | `curl -H "Authorization: Bearer $KEY" "localhost:11430/v1/workspaces/<工作区>/fs?device=<B>"` | B 工作区的目录 |
| 7.5 | 同上，换成 `/file?path=README.md`、`/log?limit=5`、`/diff?task_id=<id>` | 文件内容、最近提交、这个任务的 diff |
| 7.6 | `/file?path=../../.ssh/id_rsa` | 400「路径不在工作区里」 |
| 7.7 | 拉一个 50 MB 以上的产出文件 | 不出错（约 5–10 秒） |

**中继**（服务端部署见仓库根目录 `DEPLOY.md`「设备网络」）：

1. 部署 `mesh-relay`，服务端配 `MESH_RELAY_URLS`、`MESH_RELAY_ACCESS_TOKEN`。
2. 两台设备重新登录（证书和中继地址一起下发）。
3. 在一台上用防火墙挡掉 UDP 直连（或放在两个对称 NAT 后面），重复上面三项。

应该：`connection` 变成 `relay`，功能照常；删除设备后中继也不再放行它。

按决定 D20：打洞成功率 ≥ 80%、走中继时模型首个字额外延迟 ≤ 300 ms 就够用，否则要加第二个区域的中继。中继配置和放行接口格式没在真实中继上验证过，这一节是第一次实测。

## 已知限制

- 设备之间吞吐约 9–16 MB/s，大文件慢一些。
- 其他设备开放的模型源只在降级链里自动用；要钉某台设备，模型名写 `mine:<设备>/<模型>`。
- 签发方公钥现在随证书从云端下发；正式版要内置进客户端。
- 桌面版打包 iroh 原生模块、签名公证还没做（E1-5），桌面版要用开发模式（`npm run dev`）测。
- 不做：圈子成员互派、手机当执行节点、消息注入你正在用的会话、完全不连云端的局域网模式（E6，以后再做）。
